# 남은 작업

SC-01·02·03·07·32의 접수·재전송과 SC-11·12·13·34의 명령 실행 E2E를 구현했다. 실제 CLI 12개를 동시에 실행해 SQLite의 접수·최초 Run·반복 예산이 각각 하나인지 확인하고, 재전송의 식별자와 조회 결과를 대조한다. 데몬 없이 접수하는 범위이며 실행기 기록과 산출물이 생기지 않는 것도 확인한다. `daemon run`은 별도 프로세스로 시작·종료검사와 전처리·에이전트·후처리를 실행한다. 현재 스케줄링은 직렬이며 전체 병렬·복구·취소 계약은 아직 구현하지 않았다.

현재 사용할 수 있는 명령은 `task register FILE`, `task update FILE --if-version N`, `task enable ID`, `task disable ID`, `run submit FILE`, `run show RUN_ID --json`, `daemon run`이며 전역 `--data-dir DIR`를 앞에 지정할 수 있다. 접수 코드 0은 영속 저장 성공이다. CLI는 작업 명령을 실행하지 않는다. 다른 명령과 사람용 조회 출력은 미구현이다.

| 상태 | 작업 | 관련 시나리오 |
| --- | --- | --- |
| E2E 통과 | 같은 입력 동시 접수·재전송, 원자적 최초 Run·반복 예산 저장 | SC-01 |
| E2E 통과 | 응답 전 강제 종료 복구, 포화·비활성 중 중복, 갱신 뒤 재전송, JCS·메타데이터·해시 충돌·잘못된 JSON | SC-02·03·07·32 |
| 부분 구현 | Task 버전 CAS 갱신·활성 전환·과거 정의 보존, 입력 파서·접수 스냅샷 | SC-04~06, SC-31, SC-33~34, SC-40 |
| 부분 구현 | SQLite WAL·FULL·외래키·고유 제약·즉시 트랜잭션 | SC-02~10, SC-42 |
| E2E 통과 | 최초 검사 성공, 마지막 호출 뒤 검사, 정상 비영 agent 결과, 환경·컨텍스트·argv·stdin·로그 | SC-11·12·13·34 |
| 부분 구현 | 시작 재확인·호출 슬롯·반복 Run 생성·시간 제한. 반복 지연·시작 기한·복구 예산 미완 | SC-14~15, SC-35, SC-38 |

| 부분 구현 | JSON 오류와 접수·Run 조회. 나머지 CLI·데몬 경계 | SC-41 |

Task의 `schedule`, YAML alias, 설치 `config.yaml`은 현재 지원하지 않고 명시적으로 거부한다. 기본 설치 상한만 적용한다. 일정 등록·취소·Task 조회와 파서 전체 계약은 후속 개발 대상이며 SC-33 등의 완료를 뜻하지 않는다. 접수 환경 스냅샷을 실제 실행에 전달하는 계약은 SC-34에서 확인했다.

## 검증 기록 (2026-09-11)

- `scripts/verify.sh --fast`: 통과. 게이트와 빠른 테스트 결과이며 제품 전체 완료 판정은 아니다.
- `scripts/verify.sh`: SC-01·02·03·07·32와 각 V-01·V-02 통과(확인 15, 실패 0). 나머지 37개 시나리오는 `SCENARIO_TODO`로 남아 full은 실패한다.
- SC-02는 제품 훅 없이 가득 찬 stdout 파이프로 응답을 막고, 별도 SQLite 연결로 최초 커밋을 관측한 후 실제 CLI를 SIGKILL한다. 두 번의 재시작 제출에서 식별자·접수·Run·예산 보존과 외부 명령 미실행을 확인했다.
- SC-03은 기본 키별 상한 100건을 실제 CLI로 채워 코드 5를 확인하고 Task 비활성에서 코드 6을 확인한다. 두 상태 모두 기존 중복은 성공한다. 설치 설정은 이 검증에 필요하지 않아 미구현 상태를 유지했다.
- 중복 메타데이터 검사를 제거한 변형을 `go test -race ./...`로 실행하여 SC-07/V-02와 SC-32/V-01 실패를 확인한 후 복원했다. SC-07은 소모된 예산 상태를 주입해 재전송이 잔여 반복·사용 호출을 초기화하지 않는지도 확인한다.
- SC-07 독립 리뷰에서 버전 생략 재전송의 소모 예산 검증 누락을 확인해, 예산 소모 후 버전 생략·원버전 명시 각각 재전송 직후 잔여 반복 1·사용 호출 1을 확인하도록 보강했다. HEAD 기반 별도 복사에서 fast 통과, full 기존 5개 시나리오 통과·37개 TODO 실패를 확인했다. 버전 생략 때만 예산을 복원하는 변형을 전체 `go test -race -count=1 ./...`로 실행해 SC-07/V-02가 잔여 반복 2·사용 호출 0을 검출하는 실패를 확인했다.
- 중복 조회를 SQL `AND 0`으로 무력화한 뒤 `go test -race ./...` 실행: SC-01 두 검증과 저장소 중복 단정이 실패했다. 변형 후 원래 코드를 복원했다.
- 독립 리뷰에서도 중복 조회 무력화(`AND 0`)와 반복 잔여 예산을 0으로 만드는 변형을 전체 race 테스트로 실행해 SC-01 실패를 확인했다. 오케스트레이터는 중복 응답 때 잔여 예산을 1씩 늘리는 변형을 `go test -race ./...`로 실행해 두 검증의 실패를 재현했다.
- 저장소 단위 검증은 Run INSERT 실패를 주입해 접수·예산도 함께 롤백되는지 확인한다. JSON·Task 파서에는 퍼징 시드를 추가했다. 장시간 퍼징은 아직 수행하지 않았다.
- `go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...`: 알려진 도달 가능한 취약점 없음. 이번 의존성 도입 시 별도로 실행했으며 verify.sh의 고정 도구 준비·버전 관리 정책이 아직 없어 자동 게이트에는 추가하지 않았다.
- SQLite 드라이버는 CGO와 C 컴파일러가 필요하다. Linux arm64 게이트의 교차 타입 검사는 실제 arm64 SQLite 실행 검증을 대신하지 않는다. `--deep`과 실환경 L3 검증은 미구현이다.

후속 구현도 시나리오별 실제 E2E가 통과한 뒤에만 상태를 갱신한다. 실제 출시 전에는 Linux amd64와 arm64에서 실행하고 L3 결과와 건너뜀 사유를 기록한다.

## 실행 엔진 검증 기록 (2026-09-11)

- `scripts/verify.sh --fast` 통과(확인 90, 실패 0). `scripts/verify.sh`는 9개 구현 시나리오와 모든 V 검증 통과(확인 34, 실패 0), 나머지 33개 `SCENARIO_TODO` 때문에 실패한다.
- SC-11은 후처리를 외부 게이트로 멈춰 그 결과 저장 전에는 성공하지 않는지 확인하고, 후처리 정상 비영 종료는 `failed:after`인지 확인한다. SC-12·13은 실제 agent 산출물과 Step 순서를 대조해 마지막 호출 후 검사 및 비영 agent의 검사 진행을 확인한다.
- 실행기는 명령 시작 시 별도 SQLite 연결로 자신의 실행 의도·사용 호출 슬롯이 이미 커밋됐는지 관측한다. 모든 Step의 결과와 다음 단계는 한 트랜잭션이며 실행 중 트랜잭션을 유지하지 않는다. 프로세스 PID·그룹·부팅 및 시작 식별자를 저장한다.
- SC-34는 실제 Python 실행기의 외부 기록으로 모든 단계의 argv, stdin EOF, 예약 환경, 접수 스냅샷, Step별 0400 컨텍스트, 8 KiB 피드백, 비UTF-8 원본 로그를 확인한다. 누락 상속·예약 변수 거부와 시작검사·전처리·종료검사·agent·후처리 각각의 사라진 workdir 시작 실패도 검증한다. L2 실행기에는 `/usr/bin/python3`가 필요하며 없으면 실패한다.
- 마지막 호출 뒤 검사를 생략하는 변형을 전체 `go test -race -count=1 ./...`로 실행해 SC-12 두 검증 실패를 확인했다. 접수 환경 대신 데몬 환경을 사용하는 변형은 같은 전체 테스트에서 SC-34/V-01 실패로 검출했다. 변형은 별도 임시 복사에서 수행해 작업 트리 원본을 보존했다.
- 프로세스 어댑터 테스트는 리더 종료 후 남은 그룹 자손의 출력, 그룹 시간 초과 정지, 로그 합산 상한을 실제 프로세스로 확인한다. 이 테스트는 SC-20~26 등의 완전한 복구·상한 시나리오를 대신하지 않는다.
- 후속 과제: 직렬 데몬을 전역 Run·검사 상한과 공정한 자원 선점으로 확장, 반복 지연·시작 대기 기한·연속 Run 시간 계산, 과거 프로세스 정지 확인·검사 자동 복구·수동 해소·취소, storage_paused, 조회 전체 계약을 구현해야 한다. 현재 재시작은 결과 없는 Step을 보수적으로 `blocked:process_unknown`으로 남기며 과거 프로세스를 자동 종료하거나 재실행하지 않는다. 단순 반복 Run 생성만으로 SC-04·10·14 완료를 주장하지 않는다.

## 실행 엔진 독립 리뷰 보강 (2026-09-11)

- `/proc` 디렉터리 목록을 읽은 직후 다른 프로세스가 소멸하면 stat 읽기에서 `ENOENT`뿐 아니라 `ESRCH`도 반환한다. 후자를 데몬 전체 오류로 취급하던 경합을 수정했다. 회귀 검증은 두 소멸 오류 뒤에도 다음 생존 그룹을 찾는지 확인하며 접근 거부를 정지 증거로 오판하지 않는지도 확인한다.
- SC-34는 최초 `last_check: null`과 선점 후 시작검사·전처리·최초 종료검사의 시작검사 피드백을 포함해 7개 Step 컨텍스트를 각각 대조한다. 시작검사 피드백 저장을 삭제한 변형이 전체 race 테스트에서 SC-34/V-01 실패로 검출된다.
- SC-12 등을 공유하는 실행 검증은 독립적으로 제출한 fixture 제어값으로 각 Step의 정상 종료 코드와 호출 번호를 예측한다. 종료검사의 저장 결과를 항상 코드 0으로 바꾸는 변형이 전체 race 테스트에서 SC-12/V-01·V-02 실패로 검출된다.
- `scripts/verify.sh --fast` 통과(확인 91, 실패 0), full은 구현 9개 시나리오와 모든 V 통과(확인 34, 실패 0), TODO 33개로 실패 유지. 세 무력화 변형은 별도 복사에서 전체 `go test -race -count=1 ./...`로 검증하고 원본을 보존했다.

## 후속 개발에서 결정하거나 추가할 것

- cron 파서를 구현할 때 퍼징을 추가하고, 기존 JSON·YAML 퍼징을 장시간 실행한다.
- 릴리스 버전 스탬핑과 --version은 기존 v1 CLI 계약에 없으므로 사용자와 계약을 확정한 후 추가한다.
- 커버리지 목표와 마이크로벤치마크는 현재 도입하지 않는다. 시나리오의 실효성을 우선하며 성능 병목이 관측되면 측정 범위를 정한다.

기능 제외 목록은 [요구사항](requirements.md) 1절에 유지한다. 이 목록은 새 제품 기능을 암묵적으로 추가하는 계획이 아니다.
