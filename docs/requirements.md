# todoable v1 요구사항 참조

기준일: 2026-09-10 · 명세 버전: 1.0 · 상태: 구현 기준 확정

todoable은 외부 사건과 정기 일정으로 생긴 작업을 사용자 정의 완료조건까지 실행하는 개인용 로컬 도구다. 입력의 중복 접수와 실행 자원의 충돌을 관리하고, 실행 상태를 저장하며, 실패와 결과 불명을 구분한다.

[사용자 시나리오](scenarios.md)가 완료 판정의 최상위 규범이며, 이 문서는 v1의 상세 계약·기본값·예시를 보존하는 요구사항 참조다. 문서 위계는 사용자 시나리오 > 아키텍처·요구사항 > 코드다. 이전 설계 검토안·초안·추천안의 내용을 통합하고 대체한다. 아래 명령·형식·동작은 구현해야 할 계약이며, 이미 구현·배포되었다는 뜻은 아니다. 문서에 적힌 기본값은 성능 측정값이 아니라 v1의 기본 설정이다.

## 1. 범위와 사용 모델

지원 환경은 Linux amd64·arm64의 단일 호스트, 단일 사용자다. Go로 작성한 단일 실행 파일, 로컬 SQLite, CLI를 사용한다. 데이터 디렉터리 하나당 데몬 하나만 실행한다. Task와 외부 명령은 실행 계정이 신뢰하는 로컬 작업이다.

| 포함 | 제외 |
| --- | --- |
| 외부 스크립트의 입력 제출, 즉시 실행 | GitHub·파일함 등 외부 입력 수집기 내장 |
| 간격·cron에 따른 정기 입력 발행 | 놓친 모든 기간의 자동 일괄 보충 |
| 시작·종료 검사, 전처리·후처리 | 임의의 워크플로 DSL, DAG, 사용자 finally 훅 |
| 외부 에이전트 명령, 호출·시간·출력 제한 | 특정 에이전트 제품의 전용 연동 |
| 입력별 유한 반복, 키별 순서와 병렬 상한 | `repeat: forever`, 실행 중 입력 변경·대기 입력 합치기 |
| 영속 상태, 수동 복구, Task 버전 갱신 | 여러 호스트, 원격 워커, 다중 사용자 격리 |
| CLI 상태·로그·취소·재개 | TUI, 웹 화면, HTTP 접수 서버 |

이슈 수정, 자료 변환, 문서·색인 갱신, 정기 리포트와 점검에 같은 모델을 사용한다. 완료 결과가 파일 수정인지 커밋인지 게시인지는 Task 작성자가 정한다. 도구가 업무별 결과를 고정하거나 완료검사의 정확성을 보증하지 않는다.

외부 스크립트는 사건·원본 버전을 수집해 입력을 제출한다. 정기 작업은 명시적으로 활성화한 일정이 시간 정보를 포함한 입력을 내부 제출한다. 두 경로 모두 동일한 접수와 실행 엔진을 사용한다.

## 2. 단위와 식별자

| 단위 | 정의와 식별자 |
| --- | --- |
| Task | 사용자 정의 작업. 안정적인 `task_id`와 증가하는 `task_version`을 가짐 |
| 입력 접수 | 입력 키와 입력 내용의 한 조합을 접수한 기록. 내부 `submission_id`를 가짐 |
| Run | 한 접수의 한 실행 회차. 내부 `run_id`, 접수 내 `run_seq`를 가짐 |
| Step | 시작검사·전처리·종료검사·에이전트·후처리 명령의 실행 시도. 내부 `step_id`를 가짐 |
| 에이전트 호출 슬롯 | 한 Run에서 외부 에이전트 실행기를 호출할 수 있는 기회. `call_index`는 1부터 시작 |

`submission_id`, `run_id`, `step_id`는 생성 시 부여한 UUID이며 변경하지 않는다. 순서는 UUID나 시계 대신 DB의 증가하는 순번으로 정한다. 최초 Run의 `run_seq`는 1이다. 제출자가 별도의 요청 UUID를 만들 필요는 없다.

입력 키는 Task 안에서 같은 업무 대상을 묶는다. 충돌 키는 같은 자원을 사용하는 Run을 데몬 전체에서 묶는다. 예를 들어 이슈별 입력 키는 서로 달라도 같은 워킹트리를 쓰면 충돌 키는 같아야 한다.

입력 접수의 상태는 `active`, `completed`, `cancelled`이며 취소 진행 여부는 별도 플래그다. 하나라도 대기·실행·차단 중인 회차가 있거나 추가 회차가 남으면 active다. 모든 회차가 끝나면 completed, 명시적 취소를 마치면 cancelled다. Run은 아래에서 정의한 별도 실행 상태를 가진다.

## 3. Task 등록·버전·활성 상태

Task 등록은 버전 1의 정의만 저장한다. 등록 즉시 Run을 만들거나 정기 일정을 시작하지 않는다. 등록 직후 외부 신규 접수는 허용하고, 정기 일정은 비활성 상태다.

동일 Task ID와 동일한 정규화 정의를 다시 등록하면 기존 버전을 반환한다. 다른 정의로 같은 ID를 등록하면 충돌 오류를 반환한다. 변경은 `task update`로 수행한다. 갱신에는 예상 현재 버전이 필요하며 버전이 다르면 거부한다. 동일 정의의 갱신은 버전을 늘리지 않는다.

신규 접수는 기본적으로 현재 Task 버전을 사용한다. 제출자가 특정 기존 버전을 명시할 수도 있다. 각 접수에는 해석된 명령·프롬프트·경로·선택 환경변수·제한값·반복 설정·입력·충돌 키의 스냅샷을 저장한다. 그 접수의 모든 Run은 같은 스냅샷을 사용한다. Task 갱신은 이미 접수한 입력과 그 반복 회차를 바꾸지 않는다.

실행 파일, 외부 서비스, 참조한 원본 자체의 내용까지 자동 고정되지는 않는다. 재현이 필요한 작업은 버전이 고정된 경로·원본 참조를 사용하고 실행 명령에서 버전 일치를 확인한다.

| 조작 | 신규 외부 접수 | 정기 발행 | 기존 접수 |
| --- | --- | --- | --- |
| `task disable` | 중단 | 비활성화 | 계속 처리 |
| `task enable` | 허용 | 자동 재활성화하지 않음 | 계속 처리 |
| `schedule disable` | 변경 없음 | 중단 | 계속 처리 |
| `schedule enable` | Task 활성 상태가 필요 | 다음 예정 시각부터 시작 | 변경 없음 |
| `task cancel` | 중단 | 비활성화 | 미완료 접수 전체에 취소 요청 |

Task 전체 취소 후에도 명시적으로 다시 활성화할 수 있다. 이전 접수·취소·중복 기록은 남으며 자동 재실행하지 않는다. v1에는 Task와 접수 이력을 삭제하는 CLI가 없다.

## 4. 입력 형식과 중복 판별

외부 접수는 UTF-8 JSON 객체 하나를 받는다. 알 수 없는 최상위 필드는 거부한다.

| 필드 | 형식과 의미 |
| --- | --- |
| `task_id` | 필수 문자열. 등록된 Task ID |
| `task_version` | 선택 양의 정수. 생략하면 신규 접수 시 현재 버전 |
| `input_key` | 필수 문자열. Task 내 순서 보존 대상 |
| `input` | 필수 JSON 객체. 업무 입력 내용 |
| `concurrency_key` | 필수 문자열. 데몬 전체 실행 충돌 대상 |

Task ID는 `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`을 따른다. 입력 키와 충돌 키는 UTF-8로 1~512바이트이며 NUL과 앞뒤 공백을 허용하지 않는다. 키의 대소문자와 Unicode 표현을 임의로 정규화하지 않는다. 사용자 키를 파일 경로로 직접 사용하지 않는다.

입력은 [RFC 8785의 JCS](https://www.rfc-editor.org/rfc/rfc8785.html)로 정규화한다. 중복 객체 필드명, 유효하지 않은 Unicode, 비유한 수, 지원 숫자 범위를 넘는 입력은 거부한다. 정수는 `-(2^53-1)`부터 `2^53-1`까지만 숫자로 허용하며 더 큰 식별자는 문자열로 받는다. 일반 소수는 JCS의 binary64 의미를 따른다. 객체 필드 순서와 공백은 무시하고 배열 순서와 문자열 값은 보존한다. `1`과 `1.0`은 같고 숫자 `1`과 문자열 `"1"`은 다르다.

중복 기준은 다음 세 값이다.

```text
(task_id, input_key, JCS(input))
```

조회용 해시는 `SHA-256(JCS([task_id, input_key, input]))`으로 계산한다. 해시가 같아도 저장한 원문 정규화 값과 키를 확인한다. 해시 충돌은 명시적인 오류이며 다른 입력을 같은 접수로 합치지 않는다.

Task 버전, 충돌 키, 접수 경로, 실제 수신 시각은 이 중복 기준에 넣지 않는다. 동일 입력 재전송은 다음 순서로 처리한다.

1. 형식·크기·Task 존재 여부를 검증하고 중복 접수를 조회한다.
2. 기존 접수가 있으면 제출된 충돌 키가 기존 값과 같아야 한다. 명시한 Task 버전도 기존 접수 버전과 같아야 한다. 다르면 `metadata_conflict`를 반환한다.
3. 같으면 기존 접수와 회차 상태를 반환한다. 버전을 생략한 재전송은 현재 Task 버전이 바뀌어도 기존 접수에 연결한다.
4. 중복이 아니면 Task 활성 상태, 선택한 버전, 실행 설정, 미완료 접수 상한을 확인하고 신규 접수와 최초 Run을 함께 저장한다.

따라서 Task가 비활성·취소 상태이거나 대기열이 가득 찼어도 올바른 재전송은 기존 결과를 받을 수 있다. 중복 제출로 반복·호출 예산을 다시 부여하지 않는다. 접수 성공 응답은 DB 커밋 이후에만 반환한다.

입력 키가 같아도 내용이 다르면 새 접수다. 실행 중인 Run을 수정하지 않고 접수 순서에 추가한다. A 실행 중 B와 C가 접수되면 B와 C를 모두 보존한다. 과거 A와 정확히 같은 내용이 다시 들어오면 B 처리 이후라도 중복이다. 의도적인 재처리는 처리 세대 등 실제로 달라진 입력 내용을 제출한다.

재오픈 사건, 파일 내용 버전, 커밋, 집계 기간을 구별할 정보는 입력 내용에 포함한다. 재전송마다 바뀌는 수신 시각이나 시도 횟수는 넣지 않는다. 경로만 같고 원본이 덮어써진 자료는 새 입력으로 자동 인식하지 않는다.

## 5. 입력별 순서·반복·자원 선점

같은 `(Task ID, 입력 키)`에서는 접수 순서대로 처리한다. 가장 앞선 미완료 접수의 모든 회차가 끝나야 다음 접수를 실행할 수 있다. 다음 접수의 시작검사도 그때부터 수행한다.

`repeat`는 0 이상의 유한 정수이며 기본값은 0이다. 입력 하나에 최대 `1 + repeat`개의 Run을 발행한다. `repeat: 2`인 A 뒤에 B가 있으면 `A₁ → A₂ → A₃ → B₁` 순서다. `repeat: forever`는 등록 오류다.

성공·확정 실패·시작조건 대기 기한 초과에 따른 건너뜀은 한 회차의 종료다. 잔여 반복이 있으면 다음 Run을 발행한다. 차단은 종료가 아니며 다음 회차를 발행하지 않는다. 취소 요청이 있는 접수에는 후속 Run을 발행하지 않는다.

다음 Run 생성, 현재 Run 종료, 반복 잔여 횟수 감소를 같은 트랜잭션으로 확정한다. 추가 회차는 기존 접수 아래 새 `run_seq`로 생성하므로 외부 입력의 중복 접수 규칙에 걸리지 않는다. `repeat_delay`는 직전 회차 종료부터 다음 회차의 시작검사까지 기다릴 시간이며 기본값은 0초다.

각 Run은 새 호출 예산을 받는다. 같은 Run의 복구는 호출 예산을 초기화하지 않는다. `max_calls`는 외부 실행기 호출 슬롯 수이며 실행기 내부 모델 요청·도구 호출·API 재시도 수가 아니다.

충돌 키는 모든 Task에 걸쳐 적용한다. Run은 전처리 시작 전 충돌 키를 배타적으로 선점하고 종료까지 유지한다. 한 Run이 끝나면 반복이 남았어도 자원을 해제한다. 다른 입력 키의 실행 가능한 Run이 다음 슬롯을 얻을 수 있다.

실행 가능해진 Run에 증가하는 `ready_seq`를 부여한다. 선점은 충돌 키가 비어 있는 ready Run 중 `ready_seq`가 가장 작은 것부터 수행한다. 어떤 키가 막혀 있다고 무관한 키의 선점을 막지 않는다. 반복 회차와 차단 해소 후 다시 대기하는 Run은 새로운 순번을 받는다. 전체 running Run 수는 전역 상한을 넘지 않는다.

시작조건이 거짓인 대기 Run은 충돌 키를 선점하지 않는다. 시작검사 오류도 선점 전이면 자기 입력 키의 순서만 막는다. 이미 선점한 Run이 차단되면 기존 충돌 키를 유지한다. 특히 결과 불명 Run의 같은 키는 사용자 해소 전까지 사용할 수 없다. 정지한 차단 Run은 실행 슬롯 수에는 포함하지 않는다. 정지를 확인하지 못한 프로세스는 기존 Run 또는 검사 슬롯을 계속 차지한다.

## 6. 정기 일정

Task는 일정 하나를 가질 수 있다. 일정은 `every` 또는 `cron` 중 정확히 하나다. 일정이 없는 Task도 외부 제출로 즉시 실행할 수 있다. 일정이 있는 Task에도 외부 입력과 기간 보충 입력을 제출할 수 있다.

간격 일정은 활성화 시각을 기준점으로 저장하고 `기준점 + n × every`를 예정 시각으로 사용한다. 최초 시각은 한 간격 뒤다. `every`는 1초 이상이다. 실행 소요 시간으로 기준점을 옮기지 않는다.

cron은 분·시·일·월·요일의 5필드 숫자 형식이다. `*`, 목록, 범위, 양의 간격을 지원하며 초 필드, 매크로, 이름 표기, `L/W/#/?`는 허용하지 않는다. 분은 0~59, 시는 0~23, 일은 1~31, 월은 1~12, 요일은 0~6이고 0은 일요일이다. 일과 요일이 모두 제한되면 둘 중 하나가 맞으면 실행 기회로 본다. 하나가 `*`이면 다른 필드만 일자를 제한한다.

cron 시간대는 IANA 이름으로 저장하며 기본은 UTC다. 존재하지 않는 현지 시각은 건너뛰고, 반복되는 현지 시각은 서로 다른 UTC 시각으로 처리한다. 활성화 시각보다 엄격히 뒤인 첫 예정 시각부터 시작한다. 예정 시각은 UTC RFC3339 형식으로 보존하고 실제 시작 시각과 구분한다.

cron 정의는 등록·갱신 시 향후 8년 안에 유효한 예정 시각이 있는지도 검증한다. 예를 들어 2월 31일만 지정해 기회가 없는 일정은 거부한다. 윤초를 직접 지정하는 표현과 시각 입력은 지원하지 않는다.

내부 접수의 입력 내용은 다음 객체로 고정한다.

```json
{
  "data": {"report": "project-daily"},
  "occurrence": {
    "scheduled_at": "2026-09-10T00:00:00Z",
    "window_start": "2026-09-09T00:00:00Z",
    "window_end": "2026-09-10T00:00:00Z"
  }
}
```

`data`는 Task의 `schedule.input`이다. `window_end`는 예정 시각이고 `window_start`는 그 직전 예정 시각이다. 간격의 첫 회차에서는 활성화 기준점이 window 시작이다. cron의 직전 예정 시각은 활성화 전일 수 있다. 누락 기간을 합쳐 window를 늘리지 않는다. 내부 시간 문자열은 UTC의 정규 RFC3339Nano 표현을 사용한다.

스케줄러는 Task별로 관찰한 시각, 가장 최근의 미접수 예정 시각, 마지막 접수 시각, 생략한 시각 수를 영속 저장한다.

1. 현재까지 도래한 예정 시각을 확인하고 아직 접수하지 않은 시각 중 가장 최근 하나를 보관한다. 그보다 오래된 미접수 기회는 생략 수에 반영한다.
2. 일정의 `(Task ID, 입력 키)`에 미완료 접수가 있으면 새 일정 접수를 만들지 않는다. 외부 제출로 생긴 동일 입력 키의 미완료 접수도 포함한다.
3. 미완료 접수가 없고 접수 상한에 여유가 있으면 보관한 최신 시각 하나를 접수한다. 접수·최초 Run 생성·커서 갱신은 한 트랜잭션이다.
4. 실행 완료나 재시작 시에도 같은 규칙을 적용한다. 이미 접수한 입력은 이 과정에서 삭제하거나 최신 내용으로 바꾸지 않는다.

관찰 커서 이후의 새 기회만 계수한다. 보관 중이던 미접수 시각을 더 최근 시각으로 대체하면 이전 시각도 생략 수에 한 번 반영한다. 용량 부족이나 접수 환경 오류가 있으면 최신 미접수 시각과 `last_error`를 유지하고 최대 60초 간격으로 재시도한다. 이 동안 새 예정 시각의 관찰과 최신화는 계속한다. 한 Task의 오류가 다른 Task의 일정을 중단하지 않는다.

이 규칙은 놓친 모든 기간을 자동 보충하지 않는다. 빠진 기간이 필요한 업무는 `schedule submit --at`으로 기간마다 명시적으로 접수한다. 같은 기간을 다시 보충하면 내용 기반 중복 판별을 적용한다. 제출할 버전을 지정할 수 있어 과거 Task 정의의 기간도 재구성할 수 있다.

일정 비활성화는 미접수 기회를 폐기하고 그 수와 이유를 기록한다. 재활성화는 새 기준점과 미래 시각에서 시작한다. Task 갱신에서 schedule 객체가 바뀌면 기존 미접수 기회를 폐기하고, 일정이 활성 상태였다면 갱신 시각에서 새 일정을 시작한다. schedule 객체가 같으면 기준점·커서를 유지한다. 일정 삭제는 일정을 비활성화한다. 이미 접수한 기간에는 영향을 주지 않는다.

예정 시각의 커서는 뒤로 이동하지 않는다. 시계가 뒤로 변경되면 처리한 기회를 다시 접수하지 않고 앞으로 진행될 때까지 기다린다. 정기 발행은 로컬 DB의 접수 중복 방지를 이용하며 외부 데이터 수집을 수행하지 않는다.

## 7. Run 상태와 실행 순서

| 상태 | 의미 |
| --- | --- |
| `waiting` | 선행 접수·반복 지연·시작조건 대기 |
| `ready` | 시작조건을 통과했고 자원·실행 슬롯 대기 |
| `running` | 자원 선점 후 단계 실행 중 |
| `blocked` | 검사 오류·결과 불명·프로세스 확인 문제로 사용자 해소 필요 |
| `succeeded` | 종료검사와 성공 후처리 완료 |
| `failed` | 확정된 실패로 종료 |
| `skipped` | 시작조건 대기 기한 초과로 실행을 건너뜀 |
| `cancelled` | 취소 절차가 끝남 |

`cancel_requested`는 상태와 별도로 저장한다. 취소를 요청한 것과 완료한 것을 구분한다. 종료 상태의 Run을 다시 열지 않는다.

```text
선행 접수 종료 및 repeat_delay 대기
  → 시작검사
  → ready / 충돌 키와 Run 슬롯 선점
  → 시작조건 재확인
  → before
  → finish.check
      ├─ 충족 → after → succeeded
      └─ 미충족 → 호출 슬롯 확인
                   ├─ 남음 → agent → finish.check
                   └─ 없음 → failed:max_calls
```

생략한 시작검사는 항상 참이다. 시작조건은 입력별 가장 앞선 접수가 된 후 최초로 검사하며, 거짓이면 `poll_every` 후 다시 검사한다. 기본은 60초다. `wait_timeout`은 최초 시작검사부터 계산하고 기본값 0은 무기한이다. 선행 접수 대기와 `repeat_delay`는 이 기한에 포함하지 않는다. 유한 기한이 지나면 `skipped:start_timeout`으로 끝낸다. 거짓인 시작검사는 호출·반복 예산을 소비하지 않는다.

자원 선점 시 시작조건을 다시 확인한다. 거짓이면 자원을 해제하고 waiting으로 돌아간다. 검사 오류이고 검사 프로세스의 정지가 확인되었으면 자원을 해제하고 시작검사 오류로 차단한다. 프로세스 정지를 확인하지 못하면 선점한 자원을 유지하고 차단한다. 전처리는 이 재확인 뒤에 실행한다.

`before`와 `after`는 선택 사항이다. 전처리는 회차당 한 논리적 단계이며 성공 후 종료검사를 수행한다. 종료검사가 최초부터 참이면 에이전트를 한 번도 호출하지 않고 후처리로 간다. 후처리는 성공 경로에만 있고 실패·취소 시 항상 실행되는 정리 훅이 아니다.

| 단계 결과 | 다음 동작 |
| --- | --- |
| 시작검사 정상 코드 0 | ready 또는 선점 후 전처리 |
| 시작검사 정상 비영 코드 | 다음 검사 대기 |
| 종료검사 정상 코드 0 | 후처리 |
| 종료검사 정상 비영 코드 | 남은 호출 슬롯으로 agent, 없으면 실패 |
| agent 정상 종료, 코드 0 또는 비영 | 반드시 종료검사 |
| agent 프로세스 시작 실패 | 예약한 호출 슬롯 유지, 진단 후 종료검사 |
| before 정상 비영 코드 또는 시작 실패 | `failed:before` |
| after 정상 비영 코드 또는 시작 실패 | `failed:after`, agent로 돌아가지 않음 |
| 검사 명령 시작 실패·시간 초과·시그널 종료 | `blocked:check_error` |
| 변경 단계의 시간 초과·시그널 종료·시작 여부나 결과 저장 불명 | `blocked:outcome_unknown` |
| 명령 실행 전 Run 시간 예산 소진 | `failed:run_timeout` |

정상 비영 코드를 임의로 실행기 오류로 재분류하지 않는다. 마지막 허용 에이전트 호출 뒤에도 종료검사한다. 에이전트의 주장이나 stdout 문구로 성공을 판정하지 않는다.

입력 접수는 마지막 회차 종료 후 completed가 된다. 결과 요약에는 마지막 회차 결과와 성공·실패·건너뜀 횟수를 각각 표시한다. 마지막 성공이 과거 실패 기록을 지우지 않는다.

## 8. 외부 명령 계약

명령은 비어 있지 않은 문자열 배열이다. 첫 값은 실행 파일, 나머지는 인자다. 기본적으로 쉘을 통하지 않는다. 쉘이 필요하면 작성자가 `sh -c` 등을 명시한다. 업무 입력을 쉘 문자열에 자동 삽입하지 않는다.

`workdir`는 등록 시 존재하는 절대 디렉터리여야 하며 해석된 절대 경로를 저장한다. 명령 시작 시 경로가 없거나 접근할 수 없으면 시작 실패로 처리한다. 프롬프트·입력의 템플릿 치환 기능은 v1에 없다.

환경변수 기본 허용 목록은 `PATH`, `HOME`, `LANG`, `LC_ALL`, `TZ`다. Task의 `inherit_env`에 명시한 변수를 추가로 읽고 Task의 `env` 값으로 덮어쓴다. 이 값들은 접수한 프로세스의 환경에서 해석해 접수 스냅샷에 저장한다. 외부 접수는 CLI 환경, 일정 접수는 데몬 환경을 사용한다. 명시적으로 상속하도록 한 변수가 없으면 접수를 거부한다. 값은 상태 조회와 진단 로그에서 숨긴다. `TODOABLE_` 접두사는 예약되며 사용자 설정으로 덮어쓸 수 없다.

모든 단계에 다음 환경변수를 전달한다.

| 변수 | 값 |
| --- | --- |
| `TODOABLE_CONTEXT_PATH` | 해당 Step의 읽기 전용 컨텍스트 JSON 절대 경로 |
| `TODOABLE_RUN_DIR` | 회차 작업 산출물 디렉터리 |
| `TODOABLE_TASK_ID`, `TODOABLE_TASK_VERSION` | Task 식별자와 접수한 버전 |
| `TODOABLE_SUBMISSION_ID`, `TODOABLE_RUN_ID`, `TODOABLE_STEP_ID` | 현재 실행 식별자 |
| `TODOABLE_CALL_INDEX` | 가장 최근 예약한 agent 호출 번호, 아직 없으면 0 |

에이전트 stdin에는 다음 구조의 JSON 객체 하나를 UTF-8로 쓰고 EOF를 보낸다. 검사와 훅의 stdin은 빈 입력으로 닫으며 같은 구조를 컨텍스트 파일에서 읽는다.

```json
{
  "protocol_version": 1,
  "task_id": "issue-worker",
  "task_version": 1,
  "submission_id": "00000000-0000-4000-8000-000000000001",
  "run_id": "00000000-0000-4000-8000-000000000002",
  "run_seq": 1,
  "step_id": "00000000-0000-4000-8000-000000000003",
  "stage": "agent",
  "call_index": 1,
  "input_key": "github:example/project:issue:42",
  "input": {"issue_number": 42, "event_id": "opened-001"},
  "prompt": "이번 입력의 이슈를 처리한다.",
  "workdir": "/srv/project",
  "run_dir": "/home/user/.local/share/todoable/runs/00000000-0000-4000-8000-000000000002",
  "last_check": {
    "kind": "finish",
    "exit_code": 1,
    "stdout": "test failed",
    "stderr": "",
    "truncated": false
  }
}
```

검사 결과가 없으면 `last_check`는 null이다. 각 필드는 모든 단계에 있으며 `stage`는 `start_check`, `before`, `finish_check`, `agent`, `after` 중 하나다. stdout·stderr 피드백은 각각 첫 8 KiB로 제한하고 잘림 여부를 표시한다. UTF-8이 아닌 출력은 대체 문자를 사용한 문자열로 피드백한다. 원본 로그는 바이트로 보존한다.

컨텍스트 파일은 Step마다 새로 생성하며 기존 Step의 내용을 바꾸지 않는다. Run 디렉터리는 같은 Run의 재개에서 유지한다. 제어용 입력과 실행 설정은 DB 스냅샷에서 복원한다. 사용자 산출물의 존재만으로 완료를 판정하지 않는다. 공급자 대화 세션의 사용과 재개는 실행기 책임이며 핵심 엔진의 필수 상태가 아니다.

외부 효과의 멱등성도 실행기 책임이다. 같은 입력의 여러 회차에서 게시 한 번이 목표라면 `submission_id`와 업무 단계를 이용한 안정적인 효과 키를 사용한다. 매 회차 별도의 효과가 목표라면 `run_id`를 포함한다. 키를 전달하는 것 자체로 목적지의 중복 방지나 결과 조회를 보장하지 않는다.

## 9. 프로세스·시간·복구

각 명령은 별도의 프로세스 그룹으로 실행한다. 지원하는 작업 명령은 스스로 데몬화하거나 그룹에서 탈출하지 않아야 한다. v1은 임의의 프로세스 격리·컨테이너 실행 서비스가 아니다. 명령 완료는 관리 대상 프로세스 그룹의 종료까지 확인한 뒤 기록한다.

프로세스 기록에는 호스트 부팅 식별자, PID, 시작 식별값, 프로세스 그룹, Step 소유 정보를 저장한다. 숫자 PID만으로 과거 실행을 종료하지 않는다. 종료 요청은 TERM 후 최대 10초 대기, 이후 KILL 순서다. 정지를 확인하지 못하면 `blocked:process_unknown`을 유지하고 충돌 키를 해제하지 않는다.

명령별 시간 제한은 실제 프로세스 시작부터 계산한다. Run 시간 예산은 선점 후 시작조건 재확인을 통과해 실행 단계에 진입할 때부터 소비한다. 전처리가 없으면 최초 종료검사부터다. 선행 접수·시작조건·반복 지연 대기는 제외한다. 차단 중 프로세스 그룹의 정지를 확인한 뒤에는 소비를 멈춘다. 정지를 확인하지 못한 시간과 데몬 중단 중 실행 중이었을 수 있는 시간은 보수적으로 소비한 것으로 계산한다. 저장한 남은 예산은 재개 시 유지한다. 같은 프로세스 생존 중에는 단조 시계로 경과 시간을 측정한다.

명령을 시작할 때 남은 Run 시간과 명령별 제한 중 작은 값을 적용한다. 실행 중 제한에 걸린 변경 단계는 결과 불명으로 차단한다. 남은 Run 시간이 0이면 새 명령 실행과 재실행 허용을 거부한다. 이미 수행된 단계의 사용자 결과 확인과 취소는 가능하다. 확인 이후 새 명령이 필요하지만 시간이 없으면 `failed:run_timeout`으로 끝낸다.

데몬 재시작 시 기록된 결과가 완결된 단계는 재실행하지 않는다. 결과와 다음 단계가 기록되어 있으면 그 다음 단계부터 복원한다. 실행 의도만 있고 결과가 없으면 변경 단계는 결과 불명으로 차단한다. 실행 의도만 남은 읽기 전용 검사는 이전 프로세스 정지 확인 후 자동 재검사한다. 프로세스 확인에 실패하면 검사도 차단한다. 이미 기록된 check_error 등 차단 상태는 재시작만으로 해소하지 않는다.

자동 재실행 가능한 외부 작업을 선언하는 옵션은 v1에 없다. 사용자 복구는 특정 Run과 특정 미확정 Step을 대상으로 다음 행동을 수행한다.

| 행동 | 허용 대상과 처리 |
| --- | --- |
| `retry` | 검사는 재검사. before·after는 새 Step 시도로 재실행. agent는 종료검사를 먼저 하고 필요할 때 새 호출 슬롯으로 실행 |
| `confirm-success` | before·agent·after의 외부 결과를 사용자가 확인. before 뒤는 종료검사, agent 뒤도 종료검사, after 뒤는 성공 종료 |
| `confirm-failure` | before·after는 해당 단계 실패 종료. agent는 종료검사를 수행하며 최종 완료 여부를 다시 판단 |

검사 단계의 참·거짓을 사용자 확인으로 대체하지 않는다. 검사 오류에는 `retry`만 허용한다. 성공 확인은 종료 코드 0, 실패 확인은 사용자가 지정한 1~255의 종료 코드로 기록한다. 수동 확인 표시와 사유를 실제 실행 관측 결과와 구분해 남긴다. 후처리 성공 확인을 제외하면 단계 성공을 Run 전체 성공으로 간주하지 않는다.

모든 행동은 이전 프로세스 정지가 확인된 뒤 가능하다. OS 기록만으로 확인할 수 없는 경우 사용자가 외부에서 정지·격리를 확인한 후 `--processes-stopped`로 선언할 수 있다. 이는 자동 검증 결과가 아니라 사용자 확인으로 감사 기록에 남는다. 이 선언만으로 외부 게시 결과까지 확인한 것으로 보지 않는다.

## 10. 취소와 결과 불명의 결합

입력 취소는 먼저 취소 요청과 후속 회차 발행 금지를 저장한다. 시작하지 않은 회차는 cancelled로 끝내고, 실행 중 명령에는 프로세스 종료를 요청한다. 종료 확인 전에는 취소 완료로 표시하지 않는다.

변경 단계가 수행 중이었다가 중단되어 결과가 불명이면 `blocked`와 `cancel_requested`를 함께 유지한다. 이 상태에서는 새 작업 재실행을 허용하지 않는다. 사용자가 해당 단계 결과를 확인하면 결과를 기록하고 접수를 cancelled로 종료한다. 취소 때문에 성공 후처리나 새 반복을 실행하지 않는다.

결과를 끝내 확인하지 못하지만 그 영향을 받아들이고 중단하려면 `submission cancel --acknowledge-effects`를 사용한다. 프로세스 정지 확인은 여전히 필요하다. 최종 상태는 `cancelled`이고 `effects_unknown: true`와 사유를 보존한 뒤 충돌 키를 해제한다. 자동 취소는 이 확인을 대신하지 않는다.

취소와 완료가 경합하면 DB 트랜잭션 순서를 따른다. 취소 커밋 뒤에는 새 Step 실행 의도를 예약하거나 후속 Run을 발행하지 않는다. 이미 실행 의도를 커밋한 명령은 실제 시작 여부와 무관하게 진행 중인 요청으로 취급하고, 데몬이 취소를 확인하면 시작을 막거나 정지를 시도한다. 취소 접수 성공 시점에 모든 외부 효과가 멈췄다고 보장하지 않는다.

완료가 먼저 후속 Run을 만들었더라도 뒤따르는 취소는 그 Run을 포함한다. 상태·Step·소유 버전이 다른 늦은 통지는 무시하고 진단한다. 실제 정지와 결과 확인이 완료될 때까지 취소 요청 또는 차단 상태를 표시한다.

## 11. 기본값·상한·로그

설치 설정은 데이터 디렉터리의 `config.yaml`에 두며 데몬 시작 때 읽는다. CLI도 같은 설정을 읽는다. 실행 중 설정 재읽기는 지원하지 않는다. 설정 변경은 데몬을 멈춘 상태에서 수행한다. 실행 중인 데몬과 CLI가 읽은 설정 해시가 다르면 CLI의 변경 명령을 거부하고 재시작을 요구한다. 조회는 허용한다. 파일이 없거나 값이 없으면 아래 기본값을 사용한다. 설정 파일은 최대 1 MiB이며 `version: 1`, 아래 전역 필드와 `caps` 외의 키는 거부한다. version 생략은 1이다.

| 항목 | 기본값 | 적용 |
| --- | --- | --- |
| `max_running_runs` | 2 | 실행 중 Run과 정지 미확인으로 슬롯을 유지한 Run의 합계 상한 |
| `max_check_processes` | 4 | 시작·종료 검사 프로세스 상한 |
| `max_pending_submissions` | 1,000 | 대기·실행·차단·취소 진행을 포함한 미완료 접수 상한 |
| `max_pending_per_input_key` | 100 | 같은 Task·입력 키의 미완료 접수 상한 |
| `max_input_bytes` | 1,048,576 | input 객체의 원본 JSON과 JCS 결과 각각의 바이트 상한 |
| `max_manifest_bytes` | 1,048,576 | Task 정의 파일 상한 |
| `max_repeat` | 1,000 | Task repeat의 설치 상한 |
| `max_calls_per_run` | 100 | Task max_calls의 설치 상한 |
| `step_log_bytes` | 10,485,760 | Step의 stdout·stderr 저장 합계 상한 |
| `completed_log_retention` | 720h | 완료 접수의 상세 로그 보존 기간 |
| `completed_log_bytes` | 1,073,741,824 | 완료 접수 상세 로그의 총량 상한 |

입력 제출 JSON 전체에는 `max_input_bytes + 16 KiB`의 읽기 상한을 적용한다. 검사·시간·용량의 설치 상한은 양의 값이어야 하며 전체 상한보다 키별 접수 상한이 클 수 없다. 반복 상한은 0도 허용한다. 설치 상한을 넘는 Task나 신규 접수는 조용히 줄이지 않고 거부한다.

| Task 필드 | 기본값 | 기본 설치 상한 |
| --- | --- | --- |
| `repeat` | 0 | `max_repeat` |
| `repeat_delay` | 0s | 24h |
| `finish.max_calls` | 3 | `max_calls_per_run` |
| `start.poll_every` | 60s | 1s~24h |
| `start.wait_timeout` | 0s, 무기한 | 유한 값은 최대 720h |
| `limits.start_check_timeout` | 30s | 5m |
| `limits.finish_check_timeout` | 30s | 5m |
| `limits.before_timeout` | 5m | 1h |
| `limits.agent_timeout` | 30m | 4h |
| `limits.after_timeout` | 5m | 1h |
| `limits.run_timeout` | 2h | 24h |

위 기간 상한은 config의 `caps` 아래 같은 필드명으로 설정한다. `repeat_delay`, `start_poll_every`, `start_wait_timeout`, `start_check_timeout`, `finish_check_timeout`, `before_timeout`, `agent_timeout`, `after_timeout`, `run_timeout` 키를 사용한다. `start.wait_timeout: 0s`는 유한 상한과 별개로 허용한다. 기간 문자열은 `ns/us/ms/s/m/h` 단위의 조합이며 음수는 거부한다. 0은 표에서 명시한 필드에만 허용한다. `every`의 최대값은 8760h다.

상한 변경은 기존 접수의 스냅샷과 예산을 바꾸지 않는다. 신규 접수는 선택한 Task 버전이 현 상한을 만족하는지도 확인한다. 동시 실행·접수 개수·로그 관리 상한은 재시작한 데몬에 즉시 적용하며, 이미 저장된 초과 접수는 삭제하지 않고 줄어들 때까지 신규 접수를 막는다.

로그 상한 뒤에도 출력 파이프를 계속 소비하고 초과 바이트는 버린다. 로그 메타데이터에는 잘림 여부를 남긴다. 완료 로그가 기간 또는 총량 상한에 걸리면 오래된 완료 접수부터 삭제한다. 진행·차단 중 로그는 자동 삭제하지 않는다. 입력·Task 스냅샷, 중복 판별 정보, Step 결과, 최종 요약과 감사 기록은 자동 만료시키지 않는다. 로그 파일이 없어졌다고 완료 기록이나 중복 방지 기록을 삭제하지 않는다.

DB·로그 쓰기 실패 시 데몬은 `storage_paused` 모드로 들어가 새 외부 명령을 시작하지 않는다. 기록 가능한 결과는 계속 저장하고 기록 실패는 stderr에도 진단한다. 1초 간격의 DB 쓰기·로그 파일 생성 및 동기화 점검이 성공하면 모드를 해제하되, 결과를 저장하지 못한 변경 단계는 결과 불명으로 차단한다. 저장에 실패한 결과를 성공 기록으로 간주하지 않는다. 재시작 시에도 저장된 실행 의도와 결과 차이에 따라 복구한다. 디스크 부족을 해결하기 위해 입력이나 중복 기록을 자동 삭제하지 않는다.

## 12. Task 파일과 예시

Task는 YAML 또는 JSON 객체로 등록한다. YAML도 중복 필드명·사용자 태그·merge key를 거부하고 JSON으로 표현 가능한 값만 받는다. 정의되지 않은 필드는 오류다. Task 정의는 파싱 후 JSON 표현도 `max_manifest_bytes`를 넘을 수 없으며 입력과 정의의 중첩 깊이는 최대 64다. YAML alias 확장도 이 크기·깊이 제한을 따른다.

| 필드 | 계약 |
| --- | --- |
| `version` | 필수, 포맷 버전 1 |
| `id` | 필수 Task ID |
| `workdir` | 필수 절대 디렉터리 |
| `agent` | 필수 명령 배열 |
| `prompt` | 필수 비어 있지 않은 문자열 |
| `before`, `after` | 선택 명령 배열 |
| `env` | 선택 문자열→문자열 객체, 기본 빈 객체 |
| `inherit_env` | 선택 환경변수 이름 배열, 기본 빈 배열 |
| `start` | 선택 객체. `check`, `poll_every`, `wait_timeout`만 허용 |
| `finish` | 필수 객체. `check` 필수 명령 배열, `max_calls` 선택 |
| `repeat`, `repeat_delay` | 유한 추가 회차 수와 회차 간 대기 |
| `limits` | 위 Task 제한 필드의 기간 객체 |
| `schedule` | 선택 정기 일정 객체 |

start를 지정하면 `check`가 필요하다. start 생략은 항상 참이다. schedule은 `input_key`, `concurrency_key`, `input`과 `every` 또는 `cron` 하나를 필수로 받는다. `timezone`은 cron에만 허용하며 생략 시 UTC다. schedule.input은 JSON 객체다. 정기 입력의 시간 객체를 포함한 최종 크기가 입력 상한 안에 들 수 있도록 등록 시 검증한다.

외부 이슈를 처리하는 Task:

```yaml
version: 1
id: issue-worker
workdir: /srv/project
agent: [/opt/todoable/agent-wrapper]
prompt: |
  이번 입력에 지정된 이슈를 처리한다.
  기존 진행 내용을 확인하고 종료검사를 만족시킨다.
finish:
  check: [/opt/todoable/check-current-issue]
  max_calls: 3
repeat: 0
```

그 Task에 대한 외부 제출:

```json
{
  "task_id": "issue-worker",
  "input_key": "github:example/project:issue:42",
  "input": {
    "repository": "example/project",
    "issue_number": 42,
    "action": "reopened",
    "event_id": "reopen-002"
  },
  "concurrency_key": "workdir:/srv/project"
}
```

정기 리포트 Task:

```yaml
version: 1
id: daily-report
workdir: /srv/reports
agent: [/opt/todoable/report-wrapper]
prompt: |
  입력의 occurrence.window_start 이상 window_end 미만 기간을 집계한다.
  그 기간에 대응하는 리포트를 생성한다.
finish:
  check: [/opt/todoable/check-report-window]
after: [/opt/todoable/publish-report-idempotently]
schedule:
  cron: "0 0 * * *"
  timezone: UTC
  input_key: project-daily
  concurrency_key: reports:project
  input:
    report: project-daily
repeat: 0
```

예시의 래퍼·검사·후처리 파일은 사용자가 제공한다. 내장된 에이전트 제품 연동이 아니다. 게시 후처리는 같은 입력에 재호출되어도 업무 의도에 맞게 중복을 제어해야 한다. 최초 종료검사를 통과한 회차도 성공 후처리를 실행한다.

## 13. CLI 계약

전역 옵션은 `--data-dir DIR`이다. 기본 경로는 `$XDG_DATA_HOME/todoable`, XDG 설정이 없으면 `$HOME/.local/share/todoable`이다. 데이터 디렉터리는 0700 권한으로 생성한다. 상대 파일 인자는 CLI의 현재 디렉터리를 기준으로 해석한다.

| 명령 | 동작 |
| --- | --- |
| `todoable daemon` | 데몬을 foreground로 실행 |
| `todoable task register FILE` | Task 등록, 기존 동일 정의는 그대로 반환 |
| `todoable task update FILE --if-version N` | Task 버전 갱신 |
| `todoable task show ID [--version N] [--json]` | 버전 정의와 활성 상태 조회, 환경변수 값은 숨김 |
| `todoable task enable ID` / `task disable ID` | 신규 접수 허용·중단 |
| `todoable task cancel ID --reason TEXT` | 전체 접수 취소 요청과 신규 접수 중단 |
| `todoable schedule enable ID` / `schedule disable ID` | 정기 일정 활성·비활성 |
| `todoable schedule show ID [--json]` | 일정·커서·최신 미접수 시각·생략 수 조회 |
| `todoable schedule submit ID --at TIME [--task-version N]` | 해당 버전 일정의 한 예정 시각을 수동 접수 |
| `todoable run submit FILE` | 외부 JSON 접수. FILE이 `-`이면 stdin |
| `todoable run show RUN_ID [--json]` | 회차와 Step 상태 조회 |
| `todoable status [--task ID] [--json]` | 미완료 접수와 회차 상태 조회 |
| `todoable logs RUN_ID [--step STEP_ID] [--follow]` | 저장 로그 조회·실시간 추가 로그 확인 |
| `todoable submission cancel ID --reason TEXT [--acknowledge-effects] [--processes-stopped]` | 입력과 잔여 반복 취소 |
| `todoable resume RUN_ID --step STEP_ID --action ACTION --reason TEXT [--exit-code N] [--processes-stopped]` | 특정 차단 Step 해소 |

`resume ACTION`은 `retry`, `confirm-success`, `confirm-failure` 중 하나다. `--exit-code`는 confirm-failure에 필수이고 다른 행동에는 허용하지 않는다. 사유 문자열은 비어 있을 수 없다. 수동 일정 접수의 TIME은 시간대가 포함된 RFC3339 시각이며 해당 버전 cron의 실제 예정 시각이어야 한다. 간격 일정 보충은 저장된 활성화 구간 안에서 그 구간 기준점에 맞는 예정 시각이어야 한다. 일정을 활성화한 적이 없는 간격 Task에는 수동 기간 접수를 거부한다. 과거 일정 활성화 구간과 버전은 보존한다.

접수·갱신·취소·재개 명령은 stdout에 JSON 결과 하나를 출력한다. 조회는 기본 사람이 읽는 형식이며 `--json`에서 JSON 객체를 반환한다. 모든 JSON 결과에 `protocol_version: 1`을 포함한다. 오류는 stderr에 `protocol_version`, `error`, `message`를 가진 JSON 객체로 출력한다. `status`와 `run show`에는 Task 버전, 입력·Run 식별자, 상태·단계, 호출·반복 사용량, 충돌 키, 선행 접수, 다음 검사·예정 시각, 마지막 검사, 시간 잔여량, 취소 요청, 차단 사유가 포함되어야 한다. `status`는 마지막으로 기록한 데몬 상태와 관측 시각도 표시하며 오래된 상태를 현재 정상 동작으로 단정하지 않는다. 새로운 응답 필드는 추가할 수 있지만 기존 필드 의미는 바꾸지 않는다.

접수 성공 결과에는 `submission_id`, `task_version`, `deduplicated`, `state`, 현재 또는 마지막 `run_id`를 포함한다. 성공적인 중복 응답은 종료 코드 0이다. 코드 0은 접수나 요청 기록의 성공이며 작업 자체의 최종 성공을 뜻하지 않는다.

| CLI 종료 코드 | 의미 |
| --- | --- |
| 0 | 성공 또는 동일 요청의 기존 결과 반환 |
| 1 | 내부·저장소 오류 |
| 2 | 형식·필드·상한 등 검증 오류 |
| 3 | 정의·버전·실행 메타데이터 충돌 |
| 4 | Task·접수·Run·Step 없음 |
| 5 | 일시적인 대기열 포화·DB 잠금·중복 데몬 |
| 6 | 비활성 Task, 잘못된 단계 조작, 프로세스 미확인 등 현재 상태에서 불가 |

CLI는 짧은 DB 트랜잭션으로 요청을 기록하며 작업 명령을 직접 실행하지 않는다. 데몬은 최대 1초 간격으로 변경을 확인한다. 데몬이 없어도 정의 등록과 외부 접수는 가능하다. 정기 발행과 실행은 데몬이 있어야 진행된다. 명령별 Step 실행은 이벤트 루프를 막지 않는다.

## 14. 저장·중단·내구성

SQLite DB는 로컬 디스크에 둔다. WAL, synchronous FULL, 연결별 외래키 검사, 5초 busy timeout을 적용한다. 네트워크 파일시스템을 여러 호스트가 공유하는 사용은 지원하지 않는다. 외부 명령을 기다리는 동안 DB 트랜잭션을 열어 두지 않는다.

저장 단위는 Task와 버전, 일정 상태·활성화 이력, 입력 접수, Run, Step, 자원 소유, 감사 이벤트다. `(submission_id, run_seq)`와 입력 중복 판별에는 고유 제약을 둔다. 충돌 자원 선점은 소유자와 상태 버전을 조건부로 갱신한다. 데몬 잠금과 DB 제약을 함께 사용한다.

다음 연산은 각각 원자적으로 커밋한다.

1. 중복·용량 확인, 신규 입력 접수, 최초 Run 생성.
2. 일정 커서 처리, 정기 입력 접수, 최초 Run 생성.
3. 자원·실행 슬롯 선점과 Run 소유 상태 갱신.
4. 호출 슬롯 소비와 agent Step 실행 의도 기록.
5. Step 결과 기록과 다음 단계 지정.
6. Run 종료, 반복 잔여 감소, 다음 Run 생성 또는 접수 완료.
7. 취소 요청, 후속 발행 금지, 시작 전 회차 종료.

외부 명령은 실행 의도 커밋 이후에 시작한다. 기록 직후 실제 실행 전에 죽어도 예약한 호출 슬롯을 복원하지 않는다. 이전 실행의 시작 여부가 불명확하면 보수적으로 차단한다. 상태 전이를 완료·실패 로그 파일의 존재 여부로 추론하지 않는다.

SIGTERM·SIGINT를 받으면 새 외부 명령 발행을 멈추고 실행 중 프로세스의 정지를 시도한다. 완료를 확인한 Step은 기록하고, 수행 중 중단된 변경 단계는 차단 상태로 남긴다. Task 자체를 취소한 것으로 처리하지 않는다. 강제 종료 뒤에는 동일 복구 규칙을 적용한다.

백업은 SQLite 온라인 백업 API 또는 데몬과 CLI의 DB 접근을 모두 멈춘 일관된 복사로 수행한다. 실행 중인 DB 파일 하나만 복사한 것을 정상 백업으로 취급하지 않는다. 데이터 디렉터리를 수동 삭제하거나 이전 백업으로 되돌리면 그 이후 접수·중복 기록까지 보장하지 못한다.

## 15. 완료 판정과 출시 검증 기준

다음은 원래 출시 검증 항목의 추적용 목록이다. 각 행은 순서대로 [사용자 시나리오](scenarios.md)의 SC-01~SC-27에 대응하며, 필수 실사용 검증은 SC-28~SC-30에 대응한다. 완료 판정은 해당 시나리오 E2E 통과로만 내린다. 설계 문서 작성만으로 통과한 것으로 보지 않는다.

| 시나리오 | 통과 기준 |
| --- | --- |
| 동일 입력을 동시에 여러 번 접수 | 접수 하나와 최초 Run 하나, 반복 예산 하나 |
| 접수 커밋 뒤 응답 전에 강제 종료 | 재제출로 기존 접수 반환 |
| 큐 포화·Task 비활성 중 중복 재전송 | 기존 결과 정상 반환 |
| 같은 키의 A 실행 중 B·C 접수 | 각 입력과 회차를 보존하고 A의 유한 반복 후 B·C 순서 실행 |
| A → B 뒤 과거 A 재전송 | 새 A 접수 없음 |
| Task 갱신 중 접수 경합 | 트랜잭션 순서에 따른 한 버전의 완전한 스냅샷 |
| Task 갱신 뒤 버전 생략 재전송 | 기존 접수 반환, 새 버전으로 자동 재실행하지 않음 |
| 서로 다른 Task의 같은 충돌 키 | 실제 변경 명령 중첩 없음 |
| 무관한 충돌 키 여러 개 | 전체 상한 안에서 병렬 실행, 막힌 키가 다른 키를 막지 않음 |
| Run 반복과 다른 입력의 자원 경쟁 | 회차 종료마다 자원을 해제하고 ready 순서대로 선점 |
| 최초 종료검사 참 | agent 호출 0회, 후처리 성공 후 succeeded |
| 마지막 허용 agent 호출 뒤 검사 참 | 호출 소진 실패 대신 정상 성공 |
| agent 정상 비영 코드, 종료검사 참 | 후처리로 진행 |
| after 정상 실패 | 같은 Run의 agent 재호출 없음, 잔여 반복은 정상 규칙 적용 |
| 조건이 계속 거짓 | 호출·반복 예산 유지, 설정한 유한 시작 기한에만 skipped |
| 긴 정기 작업 중 여러 시각 도래 | 미접수 기회만 최신 하나로 보충, 기존 접수 변경 없음 |
| 일정 커밋·재시작 경계에서 중단 | 같은 예정 입력의 이중 접수와 부분 커서 커밋 없음 |
| 빠진 보고 기간 수동 접수 | 정확한 직전 예정 시각부터 해당 시각까지의 입력, 재전송 중복 제거 |
| DST 시각 전환과 시계 후퇴 | 명시한 UTC 기회·커서 규칙 준수 |
| 슬롯 예약·명령 결과 기록 사이 강제 종료 | 슬롯 보존, 결과 불명 차단, 자동 변경 재실행 없음 |
| after 외부 효과 직후 결과 저장 전 종료 | 차단·동일 자원 대기, 사용자 확인 또는 명시적 효과 인정 필요 |
| 옛 프로세스가 남거나 PID 확인 실패 | 새 변경 명령과 잘못된 프로세스 종료를 방지하고 차단 |
| 차단 해소·재실행 | Step별 계약, 남은 호출·시간 예산과 감사 사유 보존 |
| 취소와 완료 경합 | 취소 뒤 새 Step 예약·후속 회차 발행 없음, 기존 예약의 정지·결과 불명 관리, 늦은 통지로 상태 덮어쓰기 없음 |
| DB·디스크 쓰기 실패 | 기록 없이 새 명령 발행 없음, 입력·중복 기록 자동 삭제 없음 |
| 출력 폭주·멈춘 검사 | 저장·시간 상한 준수, 파이프 교착과 전체 제어 루프 정지 없음 |
| 완료 로그 정리 | 상태·입력·중복·복구 이력 유지 |

필수 실사용 검증은 이슈 수정, 독립 자료 여러 개의 변환, 기간별 리포트 세 가지다. 외부 사건 수신과 에이전트 래퍼는 별도 스크립트로 연결한다. 실제 에이전트 연결 전에 가짜 실행기로 상태 전이와 강제 종료 시나리오를 검증한다. 외부 게시의 중복 방지는 결과 불명 시 자동 재실행하지 않는 엔진 동작과 목적지 확인을 수행하는 실행기 동작을 함께 확인한다.

v1의 구현 완료는 위 계약을 만족하는 것을 뜻한다. 제외한 기능은 첫 버전에 구현하지 않으며 기본값·제한·실패 의미를 실행 중에 암묵적으로 바꾸지 않는다. 제품 동작을 변경할 때는 사용자 확인을 거쳐 사용자 시나리오와 이 요구사항의 버전을 함께 갱신한다.
