# 사용자 시나리오

기준: todoable v1, 계약 버전 1.0 (2026-09-10). 현재 상태: 제품 미구현, 프로젝트 골격과 검증 체계 준비.

이 문서가 완료 판정의 최상위 규범이다. 문서 위계는 사용자 시나리오 > [아키텍처](architecture.md)·[요구사항](requirements.md) > 코드다. 요구사항의 상세 형식·경계값은 각 흐름의 입력 계약이다. 시나리오를 바꿔야 한다면 구현을 멈추고 사용자에게 올린다. 단위 테스트나 골격의 빠른 검사 통과로 제품 완료를 판정하지 않는다.

SC-01~SC-27은 기존 출시 필수 검증의 순서를 유지한다. SC-28~SC-30은 필수 실사용 검증이며 나머지는 상세 계약을 실행 흐름으로 펼친 것이다. 이관 범위는 [이관 대조표](migration.md)에 기록한다.

## 실행과 관측 규칙

각 시나리오는 독립된 임시 데이터 디렉터리·Task·입력·프로세스를 준비하고 다른 시나리오의 결과에 의존하지 않는다. Task는 작업 정의, 접수는 입력 하나의 영속 기록, Run은 접수의 한 회차, Step은 외부 명령 한 번의 시도다.

| 등급 | 대상 | 실행 |
| --- | --- | --- |
| L1 | 순수 판정과 게이트 자기검증 | 항상 |
| L2 | 임시 로컬 DB·파일·관리되는 가짜 실행기를 통한 CLI/데몬 흐름 | full 이상 |
| L3 | 실제 에이전트·외부 입력·게시 목적지 | --deep, E2E_DEEP=1, 캐시 없이 |

아직 구현하지 않은 시나리오는 등급과 무관하게 SCENARIO_TODO로 보고하며 full을 실패시킨다. L3의 실제 환경이 부족하면 구체적인 사유로 건너뜀을 보고하되 전체 완료 검증은 실패한다. 출시 완료는 --deep에서 L3도 실제 실행하여 통과해야 한다. 실제 에이전트 연결 전에 L2의 상태 전이·강제 종료 검증을 통과해야 한다.

SC 번호마다 test/에 TestScenario_SC_번호 함수 하나를 둔다. 각 단계의 검증 줄을 문서 순서대로 V-01, V-02에 연결한다. verify(t, "V-01", ...)는 t.Run을 통해 실제 단정문을 실행한다. 실패 시 계약도 해당 검증 안에서 단정한다. 외부 명령의 중첩·무실행은 상태 응답뿐 아니라 독립 실행 기록과 실제 산출물을 관측한다. 기대값은 검증 대상 코드가 반환한 상수에서 만들지 않는다.

## SC-01. 동일 입력을 동시에 여러 번 접수

등급 L2. 시작 상태: 독립 데이터 디렉터리, 해당 흐름의 Task와 입력, 실행 순서와 실패 시점을 제어할 수 있는 가짜 실행기.

1. 동일 Task·입력 키·JSON을 여러 CLI 프로세스에서 동시에 제출하고 모든 응답과 DB를 조회한다.
   검증: 접수 하나와 최초 Run 하나, 반복 예산 하나. 응답과 저장 상태, 외부 실행 기록을 함께 대조한다.
2. 성공 응답 뒤 같은 입력을 다시 제출하고 최초 접수의 식별자와 Run 목록을 비교한다.
   검증: 모든 응답은 코드 0으로 같은 submission_id와 최초 run_id를 가리킨다. 접수·run_seq: 1·반복 예산은 각각 하나이며 재전송 때문에 늘어나지 않는다.
